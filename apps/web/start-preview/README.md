# TanStack Start web preview

An opt-in first migration stage for Adea's real browser workspace.

**Status:** Locally validated opt-in preview; hosted authentication acceptance and production cutover remain gated.
**Base:** `a22e1722827cf923645b7bfba07983b8dd99db27` in `adea-ai/adea`.
**Scope:** Browser host only. Native clients, Agent Sim, database schema, and Control Plane are unchanged.

## What this stage implements

TanStack Start renders the web document and mounts the current workspace through explicit browser-only loading boundaries. The existing Query, Zustand, audio, theme, settings, plugin, conventional-workspace, and optional spatial components are reused. `next/dynamic` is replaced only inside this preview build by a narrow cached, mount-triggered React loader supporting the two current import sites; other Next APIs are not emulated.

A request gateway delegates `/api`, `/auth`, `/_next`, and the legacy `/icon.svg` to a separately configured **isolated Next backend**, using a Cloudflare service binding. This preserves the current API/auth URLs and server contracts. The root route checks the existing allowlist policy on that backend before returning the Start document. The gate contains only `allowed`, `sign-in`, or `denied`, never identity/session or workspace data. Missing bindings, malformed responses, provider errors, or a stalled gate fail closed. The gateway preserves request methods and bodies, public URL, original Origin, redirects, streaming responses and separate Set-Cookie fields. It never converts an untrusted Origin to a trusted one. API authorization still runs in the existing backend on every request.

The policy extraction changes only the call site in the current Next home page. It retains the existing behavior: no configured allowlist permits the page; missing/unreadable sessions redirect to sign-in; disallowed accounts receive the original early-access page. It does not implement a replacement authentication protocol.

No production build/deploy scripts, Wrangler production bindings, deployment workflows, or DNS routes are switched. Start's build and Wrangler metadata live under this directory, separately from the shipping Next host.

## Why this is staged instead of a blanket replacement

`packages/auth/src/server.ts` uses `@neondatabase/auth/next/server`. The workspace principal, temporary-session claiming, desktop-session exchange, database lifecycle, and response helpers depend on this existing server integration. Replacing the UI framework is not a reason to weaken those contracts or improvise cookie/session handling. This stage retains Next as the auth/API service; it is **not a completed removal of Next.js**.

The nuqs documentation also explicitly says its TanStack Router adapter does not yet cover Start. The preview instead uses `nuqs/adapters/react` entirely within `ClientOnly`. String query semantics are preserved, including `roomDesigner=0`, blank flags, repeated keys, encoded values, and unknown parameters. Browser back/forward, view switching, query preservation, settings, and unavailable-engine behavior are covered by the browser suite; live engine and hosted-account acceptance remain separate. No Start server loader depends on nuqs state in this stage.

The workspace is deliberately browser-only; there is no private Query dehydration or server-side database access in the Start document. The `next/dynamic` bridge is temporary and should be removed when the Start host becomes the canonical host. This preview does not adopt experimental React Server Components.

## Installation and validation

Use Node 24.18.0 and Bun 1.4.0 in an isolated checkout. The root `bun.lock` is regenerated and frozen installation passes. Keep frozen-install enforcement enabled.

From the repository root:

```sh
bun install --frozen-lockfile
bunx turbo run build --filter=@adea-ai/web^...
bun run --cwd apps/web start:test
bun run --cwd apps/web start:build
bun run --cwd apps/web start:typecheck
bun run --cwd apps/web start:check-bundle
bun run format:check
bun run lint
bun run typecheck
bun run test:unit
```

The preview route tree is generated by the real Start build and ignored in Git. Build before `start:typecheck`. `start:check-bundle` requires both the actual client output and the build plugin's module evidence; it fails rather than reporting success without them. Module evidence is kept in ignored `.checks/`, not deployed with public assets. The client graph disallows database/auth-server modules and actual Next runtime code. Only four explicit, already-public environment variables are substituted. No blanket `process.env` or `VITE_*` export is introduced.

Because these are new dependencies, the updated lockfile and both framework builds must be reviewed together. Passing the dependency-free policies is not a substitute for the commands above, a dependency audit, or browser integration.

## Preview backend preparation

Prepare a separate Next/OpenNext Worker **from this patch** so that it contains `/api/web-entry`. Give it the distinct name `adea-web-start-backend-preview`; do not bind to production `adea-web` or its production Hyperdrive/Neon branch. Configure isolated database credentials, isolated auth cookie material, the appropriate provider test environment, and explicit trusted origins/callback URLs for the Start preview. Copy no production data or credentials into a test harness.

The Start configuration references that isolated service but does not create it. The Start Worker has no database, auth cookie secret, or Control Plane credentials. Its default configuration enables neither a custom domain nor a production route. Builds and tests never deploy either service.

For local work, launch the isolated legacy Worker under that name through Wrangler in another terminal before `bun run --cwd apps/web start:dev`. Cloudflare's Vite plugin uses local service-binding discovery; `remoteBindings: false` prevents accidental local reads from cloud services. The built local multi-Worker service binding, cookie preservation, real mutations, tenant isolation, allowlist enforcement, and disconnected-backend failure are exercised by `start:test:local`. An absent/unavailable backend must yield HTTP 503, not an open workspace.

For a deployed preview, inspect the generated Worker configuration before explicitly uploading from this preview directory. No deploy script is added in this patch, avoiding an accidental production or preview deployment. Do not run a production deploy command as a way to test this stage.

## Reproducible local and CI acceptance

After dependency and workspace builds, run:

```sh
bun run --cwd apps/web start:verify
bun run build:cloudflare
bunx playwright install chromium
bun run --cwd apps/web start:test:local
```

The runner creates an isolated Docker Compose project with restricted database roles, free ports, unique local Worker names, and loopback HTTPS. It applies reviewed migrations only to that disposable database, runs the browser suite, checks restricted entry and backend disconnection, and removes its processes and database volume. Production credentials are not inherited. Logs and gate results remain under ignored `.checks/local-*`. It does not use your normal development database.

The read-only `TanStack Start Preview` workflow runs this sequence on ready PRs without cloud secrets. Local HTTPS is necessary because production-built Next emits Secure session cookies; do not strip that attribute to make HTTP tests pass. The isolated legacy config uses OpenNext's documented `keep_names: false` workaround for serialized theme scripts; the existing production config is unchanged.

## Browser acceptance

Run against a started or deployed **isolated** Start gateway, initially with the backend's allowlist unset for the deterministic guest suite:

```sh
ADEA_START_PREVIEW_URL=https://127.0.0.1:3104 \
ADEA_START_ISOLATED_TEST_TARGET=1 \
bun run --cwd apps/web start:e2e
```

The dedicated config reuses `apps/web/e2e/workspace-guest.spec.ts` unchanged and adds a check that the page is really served by Start, without Next client chunks. It does not silently launch Next as a substitute. The new browser check produces desktop/mobile screenshots and script request evidence. Mocking the browser bootstrap keeps fixture content consistent, but the server-side entry gate still talks to the real isolated backend.

Additional **required** acceptance checks before any cutover: allowed account, disallowed account, anonymous allowlist behavior, provider outage, fresh/expired/rotated cookies, sign-in and sign-out, temporary account claiming, desktop exchange, CSRF rejection, marketplace authorization, real bootstrap/mutations, event delivery/reconnect, view changes and browser back/forward, settings hashes, deep-linked designers, and optional engine load/failure. Compare the same tests against baseline and candidate with identical test fixtures.

## Deliberate limits and rollback

This HTTP-only stage rejects WebSocket upgrades with HTTP 426. It passes HTTP response streams without buffering, but any WebSocket-dependent path must be ported and integration-tested before promotion. Framework transition telemetry beyond existing shared initialization still needs a native Start integration; do not assume the Next instrumentation hook runs in this preview. The source build guard is conservative and may reveal an additional client dependency on the Neon SDK's Next entry; do not silence it—introduce a documented browser adapter if the compiled graph requires one.

Frozen install, both production framework builds, local Workers, Bun tests, PostgreSQL integration, browser parity, and screenshots have been exercised. Live hosted OAuth/provider flows, production Cloudflare deployment, private Agent Sim, and native OS compiler checks have not been exercised for this preview. Passing local cookies and policy tests does not establish hosted OAuth parity. Generated routes, Worker bundles, raw reports, and browser artifacts remain ignored rather than committed.

Stage two should port the remaining server host and auth adapter with parity tests, or make an explicit decision to keep a separate backend. Only then replace the default commands and remove Next/OpenNext. Until that decision is validated, production remains on the existing host. Rollback of this preview requires no database migration: remove the preview deployment and revert the patch if necessary. Do not reset or delete user data.

To repeat the local comparison against two built loopback HTTPS hosts:

```sh
bun run --cwd apps/web start:compare --next-url https://127.0.0.1:3105 --start-url https://127.0.0.1:3104 --runs 5
```

This command does not launch servers. It records browser-side DOM readiness, initial resource sizes, request counts, and automation-observed view switches in `.checks/comparison`. Both hosts receive identical bootstrap fixtures, browser contexts are fresh, and order alternates. It is not a production Core Web Vitals measurement.
