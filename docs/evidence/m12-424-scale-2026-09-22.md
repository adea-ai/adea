# M12 #424 scale and storage evidence — 2026-09-22

Measured evidence for the remaining acceptance box on #424: "Performance tests
cover 100 sessions/1,000 processes without polling storms or >16 ms UI tasks;
soak verifies bounded metrics/history storage."

All numbers below are from one validation pass on this machine:

```text
Apple M2 Max, 64 GiB, macOS 26.6.2 arm64, Bun 1.4.0
checkout: feat/m12-424-scale (worktree of main @ a8b84085)
```

## Method

Two named lanes carry the evidence (both retain machine-readable summaries
under `artifacts/dev-runtime/`):

- `bun run test:scale` → `scripts/test-dev-runtime-scale.mjs` (new). Seeds the
  production registrar seams — the durable launch-record journal joined
  against a live supervision snapshot, owner resolution (10 processes per
  runtime session), and the bounded `ps` sampler over its injectable
  transport — then pulls the real `dev.resources.snapshot` handler.
- `bun run test:soak` → `scripts/test-dev-runtime-soak.mjs` (extended). Before
  the 20-round replay it drives the terminal checkpoint store and the metrics
  history past their retention caps and measures storage before/after in real
  bytes.

## Scale scenario A — 100 sessions / 1,000 processes, 500 pulls

Pulls run at the spec's visible-active cadence (2-second clock step). Budgets
and results:

| Budget                                                | Result                                         | Verdict |
| ----------------------------------------------------- | ---------------------------------------------- | ------- |
| No polling storm: exactly one `ps` per pull           | 501 observations for 500 pulls + 1 warm-up     | pass    |
| Bounded window: ≤ 64 distinct PIDs per pull           | max 64, min 64 (full window every pull)        | pass    |
| Coverage: 1,000 processes / 100 sessions              | 1,000 owners / 100 sessions with metric points | pass    |
| Sample latency per pull (sampler, scripted transport) | p95 0.09 ms (budget 16 ms p95)                 | pass    |
| UI-task analog: 1,000-row projection                  | p95 0.09 ms (budget 16 ms p95)                 | pass    |
| UI-task analog: session metric summary                | p95 0.02 ms (budget 16 ms p95)                 | pass    |
| Real transport probe: 20 pulls × 1 real `ps` spawn    | 20 spawns; p95 2.57 ms (5 s command budget)    | pass    |

Host `dev.resources.snapshot` handler (reported context, 5-second hang guard,
not the UI-task budget): p50 8.89 ms, p95 13.70 ms over the 500 pulls, with a
p95 growth trend across 50-pull buckets of
`[5.69, 6.9, 7.41, 8.68, 9.38, 10.24, 11.45, 12.68, 13.22, 29.57]` ms at
32,064 stored points (the last bucket absorbed one scheduling outlier; the
monotone climb across buckets is the signal and reproduced on every run). This
measured linear growth — the read is O(total retained points) and the
inventory rebuild is O(inventory²) — is filed as #596 with the numbers; the
UI-task budgets the issue pins hold independently of it.

## Soak — bounded storage, measured before/after

`bun run test:soak` (default 20 rounds plus the storage probes; lane passed in
13,747 ms, rounds 556–577 ms each):

Terminal checkpoint retention at the **real 256 MiB/session cap** (no cap
override — the write volume is the only acceleration):

- fed through the production checkpoint sink (real checksummed segments,
  atomic renames, per-write retention passes): 276,824,064 bytes (cap + 8 MiB)
- measured on disk after retention: **267,745,595 bytes across 256 segments —
  under the 268,435,456-byte cap**; ~9 MiB measurably evicted
- replay after retention returned the durable tail (1 newest chunk; newest
  durable sequence 4224 of 4224 written)

Metrics history at the named constants (720 points / 24 h):

- 1,721 samples pushed into one owner: stored count stayed exactly 720 before
  and after 500 further samples
- serialized history size measured before/after: **138,961 → 138,961 bytes**
  (flat once capped), and the 24-hour window held after a full-window clock
  jump

## Findings and gaps

- #596 (filed): `dev.resources.snapshot` host read cost grows linearly with
  total retained metric history (and the inventory rebuild is O(n²)); at the
  issue's 1,000-process scale the host pull p95 crosses 16 ms within a few
  hundred pulls. The pinned UI-task budgets and both retention caps hold; the
  shell source was frozen this wave, so the finding is filed rather than
  fixed.
- The soak storage probe accelerates the write volume only (cap + 8 MiB fed in
  64 KiB chunks); the cap, the store, and the retention passes are the
  production ones. The 24-hour acceptance soak (raising
  `ADEA_DEV_RUNTIME_SOAK_ROUNDS`) remains the endurance record for descriptor/
  listener/memory accumulation, as documented on #426.
