## How to read the statuses

- **pass / fail**: a measured value compared with an explicit limit, at main.
- **present / absent**: an identifier was or was not found in product source at that revision. This is a search, not proof of behavior. `absent` does not prove a feature is missing, and `present` does not prove it works.
- **partial**: a passing test that covers only part of the criterion. The limit is written next to it.
- **not-run**: the criterion has evidence, but at a revision other than `--main`, or no evidence was supplied. The observed result and its revision are kept in the record. Only evidence at `--main` can give a verdict.
- **invalid**: evidence that fails its contract. Examples: an axe artifact that is not a complete strict scan; a check-client report that arrives with a nonzero exit; a recorded axe pass without its validated audit artifact. It never passes.
- **blocked**: an attempted run that did not complete. The reason and exit code are recorded.
- **measured**: a recorded run, with its command and result.
- **not-measured**: measurable in principle but not run here. The command is in the inventory.
- **unavailable**: needs data, a person or a decision that this repository and session do not have. No value is estimated.
- **not-claimed**: this leaf makes no claim.

## Findings

1. **The Dev View axe audit and keyboard suite ran on this host, at `292c6de6`, not at main.** The strict axe audit exited 0 on 10 surfaces: chat, the Dev View terminal, the 320px layout and seven Settings tabs. It reported zero violations under the WCAG 2.2 AA axe tags. This is automated rule coverage only. It does not replace the manual assistive-technology audit (ACC-06). The keyboard suite passed 11 of 12 tests. Test `cert 2.5.8` fails: the "Resize left utility pane" separator is not attached after "Expand utility sidebar" is clicked and "Shared developer utilities" appears. Whether this is a regression or an out-of-date precondition has not been decided. Two earlier audit runs on the cold dev server exited 1 (the Settings menu item detached, then the 320px sidebar did not appear). A third run on the warm server passed. The lane has no retry, so a cold start can fail it.
2. **ADR-0010's client JavaScript table is stale.** It lists 2,350,000 raw bytes, 700 KiB gzip and no file cap. The ceilings in `scripts/client-bundle-budgets.mjs` are 3,112,000 raw bytes, 926 KiB gzip and 162 files. The last bundle measurement, at `34a3eaad`, was 3,051,665, 928,997 and 159, within those ceilings. Main has moved since then, so this is not a main measurement. This change does not edit the ADR.
3. **ADR-0010's rebuild figure is not reproduced.** The ADR cites about 7 s for a full rebuild. A cold `bun run --cwd apps/web build` took 192 s at `9fb30c49` and 251 s at `34a3eaad`. Both runs exited 0.
4. **Cost is not measured.** Budget reservation and cost-state identifiers are absent on main (COST-03, COST-04). The only zero-model-call test covers the structural-lead setup path (COST-01, partial). Metering (COST-05) and billing reconciliation (COST-06) are unavailable.
5. **Operations mechanisms are absent on main.** Metric, operator-control, feature-flag, retention-gate and export identifiers are absent. Candidate #1244 adds rollback routing identifiers and a rollback or rollout document path. Candidate #1245 adds export identifiers. Candidate #1243 adds no retention-gate identifier that this probe recognizes.
6. **The runtime latency targets are not approved.** PERF-06 (p95 admission at or below 1 s, scheduling at or below 2 s) is a proposal awaiting FOUNDATIONS approval. No benchmark exists, so nothing is measured.
7. **The OPS-07 failure in the earlier record is withdrawn.** The 10 failures at `9b60895c` came from stale build output, not from main. The comparator imports `@adea-ai/types`, which Bun resolves to its built `dist`. The commit hook for `5c831355` rewrote that output. The same unit file then passed 60 of 60, with no change to `packages/db`. The earlier statement that main itself fails these cases was wrong. The stale state was not reproduced, so the cause is inferred from the before and after runs.

## Reproduce

```sh
bun install --frozen-lockfile
bunx turbo run build --filter='@adea-ai/web^...'
bun run --cwd apps/web build
bun run --cwd apps/web start:check-bundle       # check-client report on line 2; wrap it as below
node scripts/readiness-evidence.mjs check
node scripts/readiness-evidence.mjs measure \
  --main 469001584b7984cb3c581b10cbd169fa1eda262a \
  --candidate <pr>=<sha> \
  --bundle docs/evidence/m18-1224-client-bundle-main-2026-10-10.json \
  --axe docs/evidence/m18-1224-axe-dev-view-2026-10-10.json \
  --recorded docs/evidence/m18-1224-recorded-runs-2026-10-10.json \
  --run-unit
```

Pass one `--candidate <pr>=<sha>` per row in the candidate table. Each SHA must be in the local object store (`git fetch origin <branch>`).

Every evidence file names its `revision` (a full 40-character commit SHA), its `command` and its `exitCode`. The bundle file wraps the check-client report as `{ revision, command, exitCode, report }`. The axe file wraps the audit artifact as `{ revision, command, exitCode, artifact }`. The recorded-runs file is keyed by criterion id, and each entry carries the same three fields. `measure` refuses input that does not meet this contract. Only evidence whose revision equals `--main` can give a verdict. `--run-unit` needs a clean tracked tree and labels its results with HEAD. Run it from the commit you want recorded.

The `check` command validates the inventory and exits non-zero on any error. The measure command rewrites `docs/plans/m18-readiness-measurements.json`.
