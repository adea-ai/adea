# M18 rollout and rollback guidance (#1224)

This is the entry point for operators who need to roll out or roll back an Adea candidate. It indexes the records that already exist, states what each one establishes and what it leaves open, and lists the decisions nobody has made yet. It is guidance over existing evidence. It does not authorize a deployment, a migration, a credential change or a cohort. It does not certify readiness and it does not close [#1224](https://github.com/adea-ai/adea/issues/1224).

The measurement record that goes with it is [m18-readiness-inventory](m18-readiness-inventory.md) and the run record is [m18-1224-readiness-2026-10-23](../evidence/m18-1224-readiness-2026-10-23.md). Measured at main `fed9548c5b1f7bbf319872940a0bd7de4055dbde`.

## Rollback, as the repository records it

1. **Application rollback does not reverse SQL.** Deploy an application rollback while the expanded schema is compatible, then add a reviewed corrective migration. Point-in-time restore is for data-loss recovery, not routine schema rollback ([packages/db README](../../packages/db/README.md), [database operations](../database-operations.md)).
2. **Recovery has two methods only:** a forward fix proved on a disposable instance of the same PostgreSQL major version, or a Railway backup restored into a fresh schema and compared. No legacy artifact, fallback provider or compatibility path is a recovery method ([Railway PostgreSQL recovery](../guides/railway-postgres-recovery.md)). The live steps are root-owned operations.
3. **Lead-turn rollback fence.** Existing admissions can be fenced and then observed, reconciled or cancelled through the historical boundary. See [m18-01-3-rollback-fencing](../evidence/m18-01-3-rollback-fencing.md). At main, the A31 rollback tests pass: 16 unit tests and 18 integration tests on PostgreSQL 18.6 ([run record](../evidence/m18-1224-readiness-2026-10-23.md)). That covers the fence mechanics only.
4. **After a point-in-time restore the cohort has to be fenced again.** The restored image has no fence columns and the forward-only recovery re-adds them as null, so the database cannot tell the window was ever declared. The evidence the fence classified survives, so the second declaration produces the same dispositions ([populated migration rollback outcome](../evidence/m18-populated-migration-rollback-outcome.md)).
5. **The cutover quarantine is not undone by a rollback.** After commit, recovery is forward-only. Do not drop quarantine records or recreate withdrawn grants from retained participant rows alone ([packages/db README](../../packages/db/README.md)).
6. **An admission outside the fenced cohort stays unfenced.** The product reader reports `fence_required` for it. It is never silently treated as safe.

## What an operator must not infer

- A green liveness check is not schema readiness or login acceptance.
- A passing fixture or a merged component is not production or cross-product completion.
- The A31 tests passing is not a declaration that the rollback window is safe. The record that measured the window says so in as many words.
- This document and the records it indexes ran nothing against production, and read no live instance.
